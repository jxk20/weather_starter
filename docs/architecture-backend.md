# Backend Architecture

**Single process in dev.** `backend/src/server.ts` builds one Express app (`createApp()`) that both serves `/api/*` routes and mounts Vite in middleware mode (`appType: 'spa'`) to serve the React frontend. There are no separate frontend/backend ports or CORS config — the frontend always calls relative `/api/...` paths. In production (`NODE_ENV=production`), Vite middleware is replaced by `express.static` over `frontend/dist` with a catch-all to `index.html`.

`createApp(options)` accepts an injectable `weatherClient` and toggles for `serveFrontend`/`enableRequestLogging` — this is how `locations.test.ts` runs the router against a fake weather client without hitting the real API or starting Vite.

**Snapshot-not-timeseries data model.** Each row in `locations` (SQLite via `backend/weather.db`) holds one lat/lon plus the *latest* weather snapshot flattened into columns (`backend/src/schema.ts`). There is no history table. Creating a location immediately fetches and stores one snapshot; refreshing overwrites it in place. (Feature Task 8 in the README describes adding a real time-series/readings table if that's ever needed.)

**Drizzle over `node:sqlite`, not better-sqlite3.** `backend/src/db.ts` wires Drizzle's `sqlite-proxy` driver over Node's built-in `node:sqlite` (`DatabaseSync`), with a hand-rolled `sqliteCallback` translating Drizzle's run/get/all/values calls into `node:sqlite` statement calls. Migrations run automatically at import time via `drizzle-orm/sqlite-proxy/migrator` against `backend/drizzle/*.sql`, so `db.ts` has import-time side effects — importing it opens/migrates the DB immediately. Schema changes must go through `npm run db:generate` (writes new SQL under `backend/drizzle/`) before `npm run db:migrate` picks them up.

**Weather client is one class with many endpoints.** `backend/src/weather.ts`'s `SingaporeWeatherClient.getCurrentWeather()` fans out to ~9 data.gov.sg endpoints in parallel (2-hr forecast, air-temperature, humidity, rainfall, wind speed/direction, UV, PSI/PM2.5, 24-hour forecast, 4-day forecast) and merges them into one `WeatherSnapshot`. Each sub-fetch is wrapped to fail soft (`.catch(() => null)` or `safeNearestReading`), so a single upstream endpoint failing degrades that field to `null` rather than failing the whole refresh. Nearest-station/area/region matching is done locally with simple squared-distance comparisons (`nearestAreaName`, `nearestRegionName`, `nearestStation`) — no external geo library. The 4-day endpoint uses a different legacy host (`api.data.gov.sg`) than everything else (`api-open.data.gov.sg`).

Coordinate validation is enforced server-side in `backend/src/routes/locations.ts` (`POST /api/locations`) to a fixed Singapore bounding box (lat 1.1–1.5, lon 103.6–104.1); it's the only correctness gate before a duplicate-location check (unique lat/lon index) and the initial weather fetch.
